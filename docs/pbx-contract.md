# Контракт с PBX

## AMI

Набор рассчитан на Asterisk/PJSIP и одну AMI-интеграцию на экземпляр HA.
Upstream action `asterisk.send_action` глобален и не содержит селектора config
entry. Не добавляйте несколько PBX, ожидая выбор сервера по action.

На стороне companion PBX-генератора локальная настройка имеет вид:

```json
{
  "home_assistant": {
    "enabled": true,
    "ami_client_ipv4": "192.0.2.20",
    "allow_originate": false,
    "assist": {
      "enabled": false,
      "host_ipv4": "192.0.2.20",
      "sip_port": 5060
    }
  }
}
```

`192.0.2.20` — адрес для документации, **не рабочий адрес дома**. Замените его
локально. `ami_client_ipv4` должен совпасть с адресом, который PBX наблюдает для
HA. AMI слушает LAN IP PBX:TCP5038; firewall и AMI ACL допускают только выбранный
HA адрес `/32`. Для удалённого HA сначала создайте доверенный VPN-маршрут.
Интеграция выбранной версии использует обычный AMI TCP без TLS-настроек.

Username `homeassistant` и случайный secret хранятся в приватном
`.local/ha-ami-secret.json` на стороне PBX. В HA их вводят через UI, без вставки
в package/dashboard. PBX не должен использовать SIP-пароли телефонов для AMI.

Проверенный профиль прав: `read=call,dtmf`, `write=system`. Для Originate
добавляется `originate`, только если `allow_originate:true`.
**Это не read-only аккаунт:** `system` нужен discovery upstream, но также
разрешает сильные AMI-действия, включая Hangup и ModuleLoad. Наши кнопки
не сужают полномочия самого аккаунта. Разрешайте интеграцию только доверенному HA,
ограничивайте его администраторов и не открывайте AMI в интернет. Для строгого
read-only мониторинга нужна другая архитектура/модификация upstream с отдельно
проверенным контрактом.

Для кнопки `201 → 202` оба PJSIP endpoint и context `home` должны существовать.
AMI Originate сначала вызывает `PJSIP/201`; после ответа Asterisk исполняет
extension `202` в `home`. Это не одновременный вызов двух аппаратов. Общий
пример не настраивает SIP trunk или внешние номера.

## Assist: отдельный путь до номера 630

После проверки Voice over IP и audio path включите `assist.enabled:true` и
передайте реальный IP/порт HA. Номер `630` должен маршрутизироваться на PBX
к HA SIP/UDP, с сохранением исходного внутреннего номера в From. SIP телефонов
может оставаться TCP; эти две transport-настройки независимы.

Для рассматриваемой HA 2026.10 native VoIP работает с **Opus**. Cisco 7945G в
нашем профиле использует G.711. Нужен **реальный двусторонний transcoder**
G.711↔Opus в Asterisk. Наличие `opus` в списке formats или SDP pass-through
само по себе не подтверждает transcoding. На PBX проверьте модули, translation
path и живой звонок со звуком. В PBX-проекте проверен Wazo codec_opus на Asterisk 22.11.0 / ARM64: модуль
загружается и оба translation paths доступны. Это не проверка amd64-сборки
домашнего узла и не приёмка реального разговора. На своей архитектуре повторите
проверку модуля, translation и живого аудио.

Добавьте Voice over IP через Devices & services, настройте Assist pipeline,
совершите пробный вызов 630 и разрешите обнаруженному телефонному устройству
доступ к вызовам по настройкам вашей версии HA. Сверьте номер устройства с From,
затем выберите нужный pipeline. Фактические entity ID VoIP не предполагаются
в нашем renderer.

SIP: выбранный UDP-порт HA (обычно 5060). RTP: разрешённый между PBX и HA
медиатрафик по согласованным SDP-портам. Не считайте, что открытие одного SIP-порта
разрешает аудио. Проверяйте диапазоны именно запущенных версий HA и PBX.
Пакеты RTP не должны идти через HTTP Ingress.

Ни AMI, ни этот репозиторий не требуют HTTP/WebSocket bridge. Для облачного
conversation/STT/TTS аудио/текст может уходить провайдеру; для локальности
выбирайте локальные провайдеры и проверяйте маршруты.
